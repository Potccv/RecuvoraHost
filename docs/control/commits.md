# 领域提交与历史约束

本文说明领域历史、跨域提交顺序、目标身份与证据有效性的约束。它们是公共 API 的使用前提，不指定存储或运行方案；入口见[调用契约](../api/rust.md)。

## 持久提交与历史恢复

Host 服务保存提案所需的完整事件或命令、原始可信配置及提交身份，原子比较 `CommitRequest.expected_revision` 后持久提交，再通过 `CommitReceipt::confirmed` 确认。请求同时绑定领域和逻辑输入；同 ID 的内容冲突必须拒绝。提交结果不确定时先核实持久事实，不安装推测的新状态，不重新发放已消费许可。

| 领域 | 传输与恢复入口 |
| --- | --- |
| 故障 | `IncidentLedger::entries` 输出 `IncidentEntry`，`restore` 校验顺序和完整观察事务 |
| 审批 | `ApprovalLedger::entries` 输出 `ApprovalEntry`，`restore` 校验操作、政策、审核与一次消费事实 |
| 恢复编排 | `RecoveryState::entries` 输出 `RecoveryEntry`，`restore` 重复状态迁移及操作、证据关联校验 |
| 经验 | `KnowledgeCommand` 输出可信命令内容；`snapshot` 输出完整经验数据；`replay` 使用可信重建的 `KnowledgeReplayEntry` 重复命令与确认校验 |

可反序列化的事件和查询记录不是外部Host 服务直接安装权威状态的权限。Host 服务只从受保护的完整已提交历史调用恢复入口，不把模型输出或外部知识响应当作本地历史。可信经验断言和提交确认没有直接反序列化入口；知识查询快照也不能直接替代已验证命令重放。

审批恢复后通过 `prepare_recovery` 提交恢复转换；恢复编排在 `restore` 后要求先提交 `RecoveryEvent::Recover`，再接受后续变更。中断执行继续阻塞并按 Unknown 处理；待审批任务进入 `Paused`，需要显式 `Resume`。恢复不重新发出原执行许可，也不自动重复外部动作。具体阶段见[恢复流程](recovery.md)。

## 增量绑定与历史导出

提交使用带版本前缀 `recuvora-chain-v1:` 的 SHA-256 摘要绑定先前配置和全部有序事件。摘要输入为递归按键排序、紧凑编码的 JSON；数组顺序保留。起点绑定领域名称和原配置；故障与审批每条历史包含 `prior_digest` 并由完整条目推进摘要，恢复与知识由完整提交请求推进摘要。请求继续包含完整新事件或命令、配置及相应时间，Host 服务仍负责稳定聚合身份与原子版本比较。修改配置或历史前缀而保留后续绑定会被拒绝；摘要不是签名，也不证明历史来源可信。

聚合内部的有序集合、历史向量和不可变记录使用结构共享，提案只复制变动路径和被修改的记录。提交 ID 索引保留全部去重身份，故障重试在请求编码前判断。完整历史仍保留，内存随安全事实增长；领域互斥等校验仍可能扫描记录，不能据此承诺所有操作都是常数成本。

故障、审批及恢复的 `latest_entry()` 返回最新条目的只读引用，Host 服务用 `pending.state().latest_entry()` 取得本次需原子持久保存的事件；`entries()` 显式复制并返回完整 `Vec<Entry>`，适合导出和维护，不应在每次提交时调用。`restore` 接受实现 `AsRef<[Entry]>` 的输入，使用相同领域校验与摘要验证重建状态。历史导出、序列化和完整重放仍需遍历全部历史；本契约没有裁剪安全事实或跳过校验的检查点入口。

## 故障身份与样本

`ProblemContext.occurrences` 表示单个故障中的异常样本数，不授予额外修复次数或执行权限。`Register` 根据独立故障身份去重；同一故障再次登记沿用原任务，同目标尚有非终态或 Unknown 任务时拒绝新登记。

新任务以 `IncidentEvidence` 绑定当前活动故障及其记录版本号。Host 服务不得通过重新分配故障身份或裁剪历史绕过同目标互斥及原操作关联。经验匹配提供参考，不以异常样本数自动选择动作或跳过审批。

## 共享目标所有权

`TargetAuthority { target_id, epoch }` 表达稳定目标身份与所有权代次。同一实际目标必须映射到同一逻辑身份；输入所声明的所有权必须已经成立。该类型不实现锁或租约，也不能证明外部互斥。

Host 服务在消费审批许可、提交恢复执行授权和实际派发之间持有同一有效所有权，并保证当前故障记录版本和活动状态在该边界内不会失效。普通读取后的快照不能证明提交时条件仍成立。所有权代次改变或故障已解除时，不能使用旧提案继续派发。

异常退出、超时、取消与连接断开不证明执行者停止。Host 服务应保留存在执行意图、Unknown、未确认在途调用或不确定提交的目标归属，直到核实对应事实；释放前停止新派发、等待在途调用结束并确认没有剩余执行权威。Host control 的内存互斥判定只覆盖提供给它的聚合，不能替代多个Host 服务实例之间的排他协调。

## 跨域提交顺序

1. 先提交恢复任务中的原始 `ProposedOperation`，确认后处理 `RecoveryEffect::RequestApproval`。Host 服务用完整操作查找或创建审批，再提交恢复域的 `ApprovalAttached`。在两域提交之间中断时，按原操作身份查找已有审批，不能生成新操作或重复审批。
2. Host 服务完成当前故障、环境、硬政策和目标归属检查，在保持并发门控的条件下提交审批 `Consume`。确认得到 `ExecutionPermit` 后，把许可移入 `RecoveryCommand::AuthorizeExecution`；只有恢复授权也可靠提交并确认后，才处理 `RecoveryEffect::Execute`。
3. Host 服务在发送会话内具体动作前提交 `RepairActionPrepared`，保存完整 `RepairArtifact` 及绑定来源。会话最多一个动作，Host 服务校验实际能力支持与当前条件。保留不可复制许可直到执行回执可提交，通过 `ApprovalLedger::prepare_complete` 先提交审批执行结果，再把对应审批事实和回执交给恢复域的 `ExecutionRecorded`。之后的业务验收独立提交，动作执行成功本身不是业务成功。
4. Unknown 核实时，Host 服务先把独立执行证据和业务验收作为 `ResultChecked` 提交到恢复域；审批仍是 Unknown 时只保存证据，不产生最终交付或释放结果。随后以这些已验证证据提交审批 `Reconcile`，再用同一组证据和更新后的记录版本、审批事实提交 `ResultChecked`，最终完成流程。

这些步骤不假设多个存储天然支持同一事务。Host 服务必须保留跨域关联和中断时的已有事实，不把某一域的状态当成另一域已经提交的证明。目标当前健康不能代替独立执行证据，确认未执行也不能自动重发原许可。

## 经验总结、交付与隔离

恢复域确认业务结果时同时建立稳定 `ExperienceJob`。失败或 Unknown 对应实际动作的版本隔离先在恢复域提交；知识存储不可用不会移除隔离。已经结束的业务任务不因经验尚未交付而继续占据未结束任务位置；Unknown 本身仍保持阻塞。

Host 服务从 `ExperiencePending` 或 `pending_experiences()` 取得总结任务，提交 `BeginExperience` 后处理只读 `SummarizeExperience`。总结成功通过 `ExperienceSummarized` 保存报告；失败通过 `ExperienceFailed` 记录原因。重试保留经验身份和已消耗尝试次数，只调用总结能力，不重新派发修复。恢复清除在途总结调用关联，使旧回调失效。

完成总结后，`ExperienceJob.record()` 从受保护任务、执行轨迹和验收生成 `RepairExperience`。Host 服务通过 `TrustedRepairExperience::attest` 与 `RecordExperience` 保存知识域事实，再提交 `ExperienceDelivered`。相同经验 ID 的完全相同重试幂等，内容冲突必须拒绝。失败与 Unknown 的实际动作在知识域继续永久隔离；后来的成功不撤销早期事实。

总结中的候选只登记不可变产物，不继承业务结果为执行或验收证明。Host 服务保存每个未交付任务的稳定身份和完整内容，不能以替换身份、删除负面结果或改写动作版本来消除冲突。知识模型、检索与容量范围见[知识接口](../../src/control/recovery/knowledge/README.md)。

## 数据维护

Host control 只限制领域集合容量和输入大小，不提供物理数据维护接口。原配置参与提交绑定，改变历史配置不能被当作普通恢复。

维护必须保留操作身份、审批关联、一次消费、经验幂等键、不可变动作内容及失败、Unknown 和隔离事实。保留事件顺序与原故障身份，不能通过删除旧记录或重编号来绕过容量或授权限制。知识域仅支持受校验的单调容量扩展，见[知识接口](../../src/control/recovery/knowledge/README.md#逻辑容量)；当前没有通用历史裁剪、可安装检查点或其他配置迁移入口。

恢复输入必须来自同一确定的已提交历史。校验失败时不得安装部分状态、删减损坏历史或重放外部动作。纯领域回放成功只证明输入通过当前规则，不证明外部提交或实际业务恢复；证据范围见[测试与验证](../development.md)。

## 执行提交的并发条件

Host 服务在审批消费与流程派发提交期间必须保持目标所有权，并原子核验当前故障、审批记录版本及知识隔离状态。传入 Host control 的不可变快照只证明本次计算使用了哪些事实，不能保证提交时其它实例没有改变这些事实；使用事务条件或可信互斥边界处理该间隙。

审批许可已经消费但流程派发准备失败时，不得把“没有发出动作”直接记录为普通执行失败并丢弃原关联。Host 服务先将审批保守转 Unknown，再将关联结果输入流程，提交独立的未执行证据，最后执行审批核实与流程终结。已经终结的审批在任务回执缺失时也可通过 ApprovalAttached 或 ApprovalResolved 进入 Unknown 核实路径，不重新发放许可。

经验交付与业务状态分离，但失败和 Unknown 的隔离必须随结果先提交。保存或总结重试不得覆盖之前的执行事实，不能将经验可用性当作重新派发条件。Host control 只恢复当前协议的完整历史，恢复配置版本为 2；不提供旧历史导入或快照直装入口。
